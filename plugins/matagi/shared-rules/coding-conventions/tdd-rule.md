# TDD（Test-Driven Development）ルール

プロジェクトにおける TDD の核心哲学・開発サイクル・コーディング標準の定義。Kent Beck の Canon TDD（t-wada 氏解説 https://t-wada.hatenablog.jp/entry/canon-tdd-by-kent-beck）に基づく。テストを書く／TDD で進める場合 常に本ルールに従う。

## 1. 核心哲学: テスト駆動

TDD の目的 = システムを以下4状態に導く:

1. それまで動作していたもの 引き続き全て動作
2. 新しい振る舞い 期待通り動作
3. システム さらなる変更の準備完了
4. プログラマとその同僚 上記に自信を持つ

- **テストが開発を駆動:** プロダクトコード = 失敗するテストを通すためにのみ書く。テストは後付けでなく、仕様であり設計のドライバー。
- **リファクタリングへの自信:** 網羅的テストスイート = セーフティネット。安心して継続的リファクタ・改善可能。
- **テスタビリティ＝良い設計:** テストしにくいコード = 設計悪い兆候。テストしやすいコード優先→疎結合・高凝集アーキテクチャに自然と導かれる（[[design-rule]]）。
- **TDD = 手段、目的化しない:** TDD 実践自体が正当性を生むわけではない。採用手法が何であれ、仕事の質に責任を持つのはプログラマ自身。

## 2. 開発サイクル: List-Red-Green-Refactor-Commit

「Red-Green-Refactor」通称は不完全。正確には「**リスト・レッド・グリーン・リファクタ**」。リスト省略→開始条件・終了条件曖昧、インクリメンタル設計喪失、テスト項目を先にまとめて書く誤った実践を招く。

どんな小さな変更でも この反復サイクルに従う。コード生成時 現在フェーズ明示。フェーズ飛ばし禁止。

**Refactor（Phase 3）の実施粒度**: Red-Green（Phase 1-2）= テストリスト（Phase 0）の1項目ごと反復。Refactor（Phase 3）= この反復に含めず、テストリスト全項目の Red-Green 完了後に、まとめて1回だけ。実装（Green）とその後設計改善（Refactor 適用）= 同一産出者が担う。レビュー単位を「1テスト項目」でなく「1issue全体」にまとめれば、局所最適な改善に留まらず全体見渡した設計判断しやすい。テスト項目数少なくても この粒度は変更しない。この分離後、Phase 1-2 の1回の反復 = 「周」、List（Phase 0）から Commit（Phase 5）までの一連 = 「サイクル」（他ルール・スキルで「サイクル」参照する場合 この単位に従う）。

### Phase 0: List — テストリストを洗い出す

- **目的:** 検証すべき振る舞いシナリオを分析・列挙。
- **アクション:** 正常系動作・エラーケース・エッジケース・既存機能への影響回避を洗い出しリスト化。
- **条件:** この段階で実装設計判断を混ぜない。テスト = 「どう呼び出されるべきか」（インターフェース設計）と「どう実装するか」（実装設計）に分かれ、後者 = Phase 3（Refactor）で扱う。
- **リストは固定ではない:** 作業中 新項目に気づいたら随時リスト追加。既存設計との矛盾判明時 リスト見直す判断をする。

### Phase 1: Red — 失敗するテストを書く

- **目的:** リストから1項目選び、その振る舞いのインターフェース定義。
- **アクション:** 準備・実行・検証（アサーション）備えた自動テストを「1つだけ」書く。アサーションから逆算して書くと良い。
- **禁止事項:** リスト全項目を先にまとめてコード化しない／アサーションないテストで済ませない／期待値としてテスト対象出力をそのまま貼り付けない（ダブルチェックの意味喪失）。
- **条件:** 対応実装が未存在のため、このテスト = 失敗（**RED**）すること。

### Phase 2: Green — テストを通す

- **目的:** 選んだテストが定義した要件を満たす。
- **アクション:** 失敗するテストを通す最小限コードを書く（**GREEN**）。リファクタと同時に行わない（「まず動かし、その後に正しくする」順序を守る）。
- **条件:** 余分な機能を足さない。この段階の目標 = 優雅さでなく、テストを通すことだけ。
- **Green 到達時:** 新テスト項目に気づいたらリスト追加。既存設計との矛盾判明時 見直す判断をする。

### Phase 3: Refactor — 設計を改善する

- **目的:** 全テスト緑に保ったまま、ここで初めて実装の設計判断を行う。
- **タイミング:** テストリスト（Phase 0）全項目の Red-Green（Phase 1-2）完了後に、まとめて1回（Phase 1-2 の反復のたびには行わない。「Refactor の実施粒度」参照）。
- **アクション:** 通るテストの安全のもと内部構造改善。重複除去（DRY）・命名改善・複雑ロジック単純化・下記コーディング標準充足など。設計原則 = [[design-rule]] に従う。
- **禁止事項:** 次のテストへの不安からの逃避としての過剰リファクタ／重複を早すぎる抽象化の指令として扱うこと（重複 = ヒント、指令ではない）。
- **条件:** リファクタリング中も全テスト **GREEN** であり続けること。
- **Refactor 中の新規項目:** 新テスト項目に気づいた場合 リスト追加。ただし現在の Refactor では扱わず、次サイクルの Phase 1 から着手。

### Phase 4: 反復

テストリストが空になるまで Phase 1〜2（Red-Green）繰り返す。各 Green 到達時 Phase 5（中間コミット）を挟む。全項目完了後 Phase 3（Refactor）へ進む。コード動作への不安が退屈に変わるまで続行。

### Phase 5: Commit — 進捗を保存する

- **目的:** 機能する作業単位を安全なチェックポイントとして記録。
- **アクション:** 各 Green（Phase 2）到達時 テスト緑確認して中間コミット。テストリスト全項目完了し Refactor（Phase 3）まで終えたら、全テスト緑を最終確認して追加コミット。
- **条件:** 各コミット = 単一の意味ある作業単位であること。コミットメッセージもその作業を簡潔に記す。

## 3. 厳格なコーディング標準と禁止事項

### 【CRITICAL】ハードコーディング禁止

いかなる形式のハードコード値も厳禁。

- **マジックナンバー:** ロジック中に数値リテラルを直接書かない。名前付き定数として定義。命名規則具体（`UPPER_SNAKE_CASE` 等）= [[coding-lint-rule]]（`shared-rules/coding-conventions/coding-lint-rule.md`）に従う。
- **設定値:** API キー・URL・ファイルパス等の環境設定 = 設定ファイル（`.env`, `config.js` 等）や環境変数から読み込む。ソースコード中に置かない。
- **ユーザー向け文字列:** UI・ログ・エラーテキスト = 定数や localization ファイルで管理、保守性と国際化に備える。

### その他の主要標準

- **設計原則:** [[design-rule]]（`shared-rules/design-principles/design-rule.md`）に従う。
- **明確で意図的な命名:** 変数・関数名 = 目的と意図を明確に伝える。
- **ガード節 / 早期リターン:** 深いネスト回避のため早期リターン優先。
- **セキュリティ第一:** ユーザー入力 常に信頼しない。XSS や SQL Injection 防ぐため入力サニタイズ、出力エンコード。
