# TDD（Test-Driven Development）ルール

プロジェクトにおける TDD の核心哲学・開発サイクル・コーディング標準の定義。Kent Beck の Canon TDD（t-wada 氏による解説 https://t-wada.hatenablog.jp/entry/canon-tdd-by-kent-beck）に基づく。テストを書く／TDD で進める場合は常に本ルールに従う。

## 1. 核心哲学: テスト駆動

TDD の目的は、システムを以下4つの状態に導くこと:

1. それまで動作していたものは引き続き全て動作する
2. 新しい振る舞いは期待通りに動作する
3. システムはさらなる変更の準備ができている
4. プログラマとその同僚は、上記に自信を持っている

- **テストが開発を駆動する:** プロダクトコードは失敗するテストを通すためにのみ書く。テストは後付けでなく、仕様であり設計のドライバー。
- **リファクタリングへの自信:** 網羅的なテストスイートがセーフティネット。安心して継続的にリファクタ・改善できる。
- **テスタビリティ＝良い設計:** テストしにくいコードは設計が悪い兆候。テストしやすいコードを優先すれば、疎結合・高凝集なアーキテクチャに自然と導かれる（[[design-rule]]）。
- **TDD は手段であり目的化しない:** TDD の実践自体が正当性を生むわけではない。採用手法が何であれ、仕事の質に責任を持つのはプログラマ自身。

## 2. 開発サイクル: List-Red-Green-Refactor-Commit

「Red-Green-Refactor」という通称は不完全。正確には「**リスト・レッド・グリーン・リファクタ**」。リストを省略すると開始条件・終了条件が曖昧になり、インクリメンタル設計が失われ、テスト項目を先にまとめて書く誤った実践を招く。

どんなに小さな変更でも、この反復サイクルに従う。コード生成時は現在のフェーズを明示。フェーズを飛ばすことは禁止。

**Refactor（Phase 3）の実施粒度**: Red-Green（Phase 1-2）は、テストリスト（Phase 0）の1項目ごとに反復。Refactor（Phase 3）はこの反復に含めず、テストリスト全項目の Red-Green 完了後に、まとめて1回だけ行う。実装（Green）とその後の設計改善（Refactor の適用）は同一の産出者が担う。レビュー単位を「1テスト項目」でなく「1issue全体」にまとめれば、局所最適な改善に留まらず全体を見渡した設計判断がしやすい。テスト項目数が少なくても、この粒度は変更しない。この分離後、Phase 1-2 の1回の反復を「周」、List（Phase 0）から Commit（Phase 5）までの一連を「サイクル」と呼ぶ（他ルール・スキルで「サイクル」を参照する場合はこの単位に従う）。

### Phase 0: List — テストリストを洗い出す

- **目的:** 検証すべき振る舞いのシナリオを分析・列挙。
- **アクション:** 正常系の動作・エラーケース・エッジケース・既存機能への影響回避を洗い出しリスト化。
- **条件:** この段階で実装設計判断を混ぜない。テストは「どう呼び出されるべきか」（インターフェース設計）と「どう実装するか」（実装設計）に分かれ、後者は Phase 3（Refactor）で扱う。
- **リストは固定ではない:** 作業中に新しい項目に気づいたら随時リストへ追加。既存設計との矛盾が判明した場合は、リストを見直す判断をする。

### Phase 1: Red — 失敗するテストを書く

- **目的:** リストから1項目を選び、その振る舞いのインターフェースを定義。
- **アクション:** 準備・実行・検証（アサーション）を備えた自動テストを「1つだけ」書く。アサーションから逆算して書くと良い。
- **禁止事項:** リストの全項目を先にまとめてコード化しない／アサーションのないテストで済ませない／期待値としてテスト対象の出力をそのまま貼り付けない（ダブルチェックの意味が失われる）。
- **条件:** 対応する実装が未存在のため、このテストは失敗する（**RED**）こと。

### Phase 2: Green — テストを通す

- **目的:** 選んだテストが定義した要件を満たす。
- **アクション:** 失敗するテストを通す最小限のコードを書く（**GREEN**）。リファクタと同時に行わない（「まず動かし、その後に正しくする」の順序を守る）。
- **条件:** 余分な機能を足さない。この段階の目標は優雅さでなく、テストを通すことだけ。
- **Green 到達時:** 新しいテスト項目に気づいたらリストに追加。既存設計との矛盾が判明した場合は見直す判断をする。

### Phase 3: Refactor — 設計を改善する

- **目的:** 全テストを緑に保ったまま、ここで初めて実装の設計判断を行う。
- **タイミング:** テストリスト（Phase 0）全項目の Red-Green（Phase 1-2）完了後に、まとめて1回行う（Phase 1-2 の反復のたびには行わない。「Refactor の実施粒度」参照）。
- **アクション:** 通るテストの安全のもとで内部構造を改善。重複除去（DRY）・命名改善・複雑なロジックの単純化・下記コーディング標準の充足など。設計原則は [[design-rule]] に従う。
- **禁止事項:** 次のテストへの不安からの逃避としての過剰なリファクタ／重複を早すぎる抽象化の指令として扱うこと（重複はヒントであり指令ではない）。
- **条件:** リファクタリング中も全テストが **GREEN** であり続けること。
- **Refactor 中の新規項目:** 新しいテスト項目に気づいた場合はリストに追加。ただし現在の Refactor では扱わず、次サイクルの Phase 1 から着手。

### Phase 4: 反復

テストリストが空になるまで Phase 1〜2（Red-Green）を繰り返す。各 Green 到達時に Phase 5（中間コミット）を挟む。全項目完了後に Phase 3（Refactor）へ進む。コード動作への不安が退屈に変わるまで続行。

### Phase 5: Commit — 進捗を保存する

- **目的:** 機能する作業単位を安全なチェックポイントとして記録。
- **アクション:** 各 Green（Phase 2）到達時に、テスト緑を確認して中間コミット。テストリスト全項目完了し Refactor（Phase 3）まで終えたら、全テスト緑を最終確認して追加コミット。
- **条件:** 各コミットは単一の意味ある作業単位であること。コミットメッセージもその作業を簡潔に記す。

## 3. 厳格なコーディング標準と禁止事項

### 【CRITICAL】ハードコーディング禁止

いかなる形式のハードコード値も厳禁。

- **マジックナンバー:** ロジック中に数値リテラルを直接書かない。名前付き定数として定義。命名規則の具体（`UPPER_SNAKE_CASE` 等）は [[coding-lint-rule]]（`shared-rules/coding-conventions/coding-lint-rule.md`）に従う。
- **設定値:** API キー・URL・ファイルパス等の環境設定は設定ファイル（`.env`, `config.js` 等）や環境変数から読み込む。ソースコード中に置かない。
- **ユーザー向け文字列:** UI・ログ・エラーのテキストは定数や localization ファイルで管理、保守性と国際化に備える。

### その他の主要標準

- **設計原則:** [[design-rule]]（`shared-rules/design-principles/design-rule.md`）に従う。
- **明確で意図的な命名:** 変数・関数名は目的と意図を明確に伝える。
- **ガード節 / 早期リターン:** 深いネストを避けるため早期リターンを優先。
- **セキュリティ第一:** ユーザー入力は常に信頼しない。XSS や SQL Injection を防ぐため入力をサニタイズ、出力をエンコード。
