# コードレビュー共通ルール

コードをレビューする全レビュアー（skills / agent）共通の判断基準の唯一の正（source of truth）。
レビュー観点の詳細解説は再掲せず、`documents/reference/code-review/google-code-review-reviewer-guide.md`（Google のレビュアーガイド日本語訳）を事実源とする。本ルールは**判断のみ**保持。

## 原則

**レビューの目的は、コードベース全体の健康状態（code health）を時間をかけて改善すること。** 完璧なコードを求めない。変更が全体としてシステムを改善すると確実にわかれば承認。追求するのは完璧さでなく継続的改善。

これがレビュー判断の最上位原則。以下の観点・重大度はすべてこの目的に従属。

## 判断基準

### 承認の閾値

| 状況 | どうする |
|------|---------|
| CL が完璧でないが、全体としてコードの健康状態を改善する | 承認（磨き上げを理由に保留しない） |
| CL がコードの健康状態を悪化させる | 承認しない（例外は緊急事態のみ） |
| 有効な選択肢が複数あり、作成者が自案の妥当性をデータ・工学的根拠で示せる | 作成者の選好を受け入れ |
| 純粋なスタイルの好み（スタイルガイドに記載なし） | ブロックしない。指摘するなら任意である旨を明示 |

技術的事実・データが個人的意見・好みに優先。スタイルはスタイルガイドが絶対的権威。

### レビュー観点（何を見るか）

設計・機能性・複雑性・テスト・命名・コメント・スタイル・ドキュメント・コンテキストを確認、良い実装は明示的に称賛。各観点で「何を確認するか」の詳細は事実源（reference のレビュアーガイド）に従う。特に：

- **設計**が最重要。全体設計に重大な問題があれば、残りを見る前に即伝達。
- **複雑性 / オーバーエンジニアリング**を警戒。将来の推測的問題ではなく、今必要なものを実装しているか。
- コメントは「何」でなく「なぜ」を説明しているか。

### 指摘の出し方

- 重大度は Critical / Warning / Suggestion の3段階で示す（定義は [[severity-rule]]）。ブロックしない細かい指摘には任意である旨（Nit 相当）を添える。
- コードについて述べ、人について述べない。理由（なぜ）を説明。
- 問題の指摘と方向性提示のバランスを取る。修正の責任は作成者にある。
- 「あとで別 CL で直す」を安易に許容しない。緊急事態を除き、複雑性の解消は取り込み前に実施。

## やってはいけないこと

- コードの健康状態を悪化させると分かっている CL を、緊急事態でないのに承認。
- 個人的なスタイルの好みで CL をブロック。
- レビュアーが産出者（実装・修正の適用者）を兼ねる（[[review-independence-rule]] 違反）。
- 本ルールやレビュアーガイドの観点解説を各レビュアー skill / agent に再掲。ドメイン固有の該当例のみ各所に残す（[[externalization-rule]] §単一情報源）。

## 背景

レビュー系 skills・agent（frontend / ui / prompt / harness / context 等）が増える中、各レビュアーが依拠すべき「レビューの目的と承認対象」の共通基準が未明文化だった。Google のエンジニアリング実践「コードレビュー（レビュアー編）」を原典として reference に格納、判断基準の核を本ルールに単一情報源として切り出し。事実・観点の詳細解説は reference、判断は本ルール、重大度は [[severity-rule]]、役割分離は [[review-independence-rule]] が担当。
