# コードレビュー共通ルール

コードレビュー全レビュアー（skills / agent）共通判断基準の唯一の正（source of truth）。
レビュー観点詳細解説 = 再掲せず、`documents/reference/code-review/google-code-review-reviewer-guide.md`（Google レビュアーガイド日本語訳）を事実源。本ルール = **判断のみ**保持。

## 原則

**レビュー目的 = コードベース全体の健康状態（code health）を時間かけ改善。** 完璧コード求めない。変更が全体としてシステム改善と確実にわかれば承認。追求 = 完璧さでなく継続的改善。

レビュー判断の最上位原則。以下の観点・重大度すべて この目的に従属。

## 判断基準

### 承認の閾値

| 状況 | どうする |
|------|---------|
| CL 完璧でないが、全体としてコード健康状態を改善 | 承認（磨き上げ理由の保留なし） |
| CL がコード健康状態を悪化 | 承認しない（例外 = 緊急事態のみ） |
| 有効選択肢複数、作成者が自案妥当性をデータ・工学的根拠で提示可 | 作成者の選好を受け入れ |
| 純粋スタイル好み（スタイルガイド記載なし） | ブロックしない。指摘するなら任意である旨を明示 |

技術的事実・データ > 個人意見・好み。スタイル = スタイルガイドが絶対的権威。

### レビュー観点（何を見るか）

設計・機能性・複雑性・テスト・命名・コメント・スタイル・ドキュメント・コンテキスト確認、良い実装は明示的に称賛。各観点「何を確認するか」詳細 = 事実源（reference レビュアーガイド）に従う。特に：

- **設計**最重要。全体設計に重大問題あれば、残り見る前に即伝達。
- **複雑性 / オーバーエンジニアリング**警戒。将来の推測的問題でなく、今必要なものを実装しているか。
- コメント = 「何」でなく「なぜ」を説明しているか。

### 指摘の出し方

- 重大度 = Critical / Warning / Suggestion の3段階（定義 [[severity-rule]]）。ブロックしない細かい指摘 → 任意である旨（Nit 相当）添付。
- コードについて述べ、人について述べない。理由（なぜ）説明。
- 問題指摘と方向性提示のバランス。修正責任 = 作成者。
- 「あとで別 CL で直す」安易に許容しない。緊急事態除き、複雑性解消 = 取り込み前実施。

## やってはいけないこと

- コード健康状態を悪化させると分かっている CL を、緊急事態でないのに承認。
- 個人的スタイル好みで CL ブロック。
- レビュアーが産出者（実装・修正の適用者）を兼ねる（[[review-independence-rule]] 違反）。
- 本ルールやレビュアーガイドの観点解説を各レビュアー skill / agent に再掲。ドメイン固有の該当例のみ各所に残す（[[externalization-rule]] §単一情報源）。

## 背景

レビュー系 skills・agent（frontend / ui / prompt / harness / context 等）増加の中、各レビュアーが依拠すべき「レビュー目的と承認対象」共通基準が未明文化だった。Google エンジニアリング実践「コードレビュー（レビュアー編）」を原典として reference に格納、判断基準の核を本ルールに単一情報源として切り出し。事実・観点詳細解説 = reference、判断 = 本ルール、重大度 = [[severity-rule]]、役割分離 = [[review-independence-rule]] 担当。
