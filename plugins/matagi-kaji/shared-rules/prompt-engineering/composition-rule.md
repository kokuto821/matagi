# プロンプト構成要素のルール

プロンプト（スキル・サブエージェントの指示文、単発プロンプト、メタプロンプト含む）を書くときの構成要素チェックリスト。

出典: `documents/reference/prompt-engineering/the-prompt-report.md`（§1.2.1 Components of a Prompt）、`documents/reference/prompt-engineering/prompt-engineering-a-prompt-engineer.md`（PE2 の Context Specification）。

## 原則

プロンプトを書くとき、以下の構成要素が**入っているか／意図的に省いたか**を毎回確認する。要素は多いほど良いわけではない。タスクに不要なものは省く。ただし「うっかり抜けた」と「意図して省いた」を区別する。

## 構成要素チェックリスト

| 要素 | 内容 | 抜けると起きること |
|------|------|------------------|
| **指示（Directive）** | 核となる意図。何をしてほしいか／何を問うか | タスクが伝わらない。最優先で明確化する |
| **出力形式（Output Format）** | Markdown / JSON / 表 / 箇条書きなど、出力の型 | 後段処理で使えない形で返る。抽出・自動化が壊れる |
| **例示（Examples）** | タスク遂行の実演例（few-shot） | 難タスクで精度が落ちる。設計は下記「例示の設計」に従う |
| **文体（Style）** | トーン・丁寧さ・簡潔さの指定 | 用途に合わない語り口で返る |
| **役割（Role / Persona）** | 「〜として振る舞え」の役割付与 | 観点が定まらない（例: セキュリティレビュアー視点） |
| **補足情報（Additional Info）** | 背景・制約・前提など核心以外の文脈 | 前提を取り違える。ハルシネーションの余地が増える |
| **文脈指定（Context Spec）** | プロンプトと入力データの結合方法（入力は前か後か、区切りは何か） | どこがデータでどこが指示か混線する。長い入力で顕著 |

## 適用の指針

- **指示と出力形式は原則必須**。他の要素はタスク次第で取捨。
- 役割（Persona）は「どの観点で出力すべきか」が重要なタスクで効く。レビュー・診断・専門判断など。
- 文脈指定（Context Spec）は、可変の入力テキストを差し込むテンプレート型プロンプトで特に重要。区切り記号を明示し、指示とデータを混同させない。
- 要素を足すたび「このタスクに本当に効くか」を問う。冗長な役割・文体指定は逆にノイズ。

## 例示（few-shot）の設計

例示は量より質・一貫性を優先（出典: The Prompt Report §2.2.1.1）。

- **質 > 量**: 良い例を数個。誤った例・ラベルは混入させない。例を増やしても頭打ち。
- **フォーマットの一貫性**: 全例で同じ書式（区切り・見出し・順序）を保つ。書式のばらつきがそのまま精度のばらつきになる。
- **順序とラベルの偏り**: 例の並び順で結果が変わる。特定ラベルに偏った例列はモデルの出力を偏らせる。
- **対象への類似**: 実際に処理したい入力に近い例を選ぶ。
- **例が要らないなら入れない**: 単純タスクは指示だけで足りる。惰性で例を足さない。
