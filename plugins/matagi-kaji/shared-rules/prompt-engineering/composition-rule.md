# プロンプト構成要素のルール

プロンプト（スキル・サブエージェント指示文、単発プロンプト、メタプロンプト含む）作成時の構成要素チェックリスト。

出典: `documents/reference/prompt-engineering/the-prompt-report.md`（§1.2.1 Components of a Prompt）、`documents/reference/prompt-engineering/prompt-engineering-a-prompt-engineer.md`（PE2 の Context Specification）。

## 原則

プロンプト作成時、以下の構成要素が**入っているか／意図的に省いたか**を毎回確認。要素は多いほど良いわけではない。タスク不要なものは省く。ただし「うっかり抜けた」「意図して省いた」を区別。

## 構成要素チェックリスト

| 要素 | 内容 | 抜けると起きること |
|------|------|------------------|
| **指示（Directive）** | 核となる意図。何をしてほしいか／何を問うか | タスクが伝わらない。最優先で明確化 |
| **出力形式（Output Format）** | Markdown / JSON / 表 / 箇条書き等 出力の型 | 後段処理で使えない形で返る。抽出・自動化が壊れる |
| **例示（Examples）** | タスク遂行の実演例（few-shot） | 難タスクで精度低下。設計は下記「例示の設計」に従う |
| **文体（Style）** | トーン・丁寧さ・簡潔さの指定 | 用途に合わない語り口で返る |
| **役割（Role / Persona）** | 「〜として振る舞え」の役割付与 | 観点が定まらない（例: セキュリティレビュアー視点） |
| **補足情報（Additional Info）** | 背景・制約・前提など核心以外の文脈 | 前提取り違え。ハルシネーション余地増 |
| **文脈指定（Context Spec）** | プロンプト・入力データの結合方法（入力は前か後か、区切りは何か） | データ/指示の境界が混線。長い入力で顕著 |

## 適用の指針

- **指示・出力形式は原則必須**。他要素はタスク次第で取捨。
- 役割（Persona）は「どの観点で出力すべきか」が重要なタスクで効く。レビュー・診断・専門判断など。
- 文脈指定（Context Spec）は可変入力テキストを差し込むテンプレート型プロンプトで特に重要。区切り記号を明示、指示・データを混同させない。
- 要素を足すたび「このタスクに本当に効くか」を問う。冗長な役割・文体指定は逆にノイズ。

## 例示（few-shot）の設計

例示は量より質・一貫性優先（出典: The Prompt Report §2.2.1.1）。

- **質 > 量**: 良い例を数個。誤った例・ラベルは混入させない。例を増やしても頭打ち。
- **フォーマット一貫性**: 全例で同じ書式（区切り・見出し・順序）を保つ。書式のばらつき = そのまま精度のばらつき。
- **順序・ラベルの偏り**: 例の並び順で結果が変わる。特定ラベルに偏った例列 → モデル出力が偏る。
- **対象への類似**: 実際に処理したい入力に近い例を選ぶ。
- **例が要らないなら入れない**: 単純タスクは指示だけで足りる。惰性で例を足さない。
