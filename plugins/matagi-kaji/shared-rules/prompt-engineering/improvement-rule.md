# プロンプト改善（prompt improvement）のルール

既存のプロンプト・スキル・サブエージェントの指示文を**改善する**ときの原則。ゼロから書く構成は [[composition-rule]]。本ルールは「すでにあるものを直す」局面。

出典: `documents/reference/prompt-engineering/prompt-engineering-a-prompt-engineer.md`（PE2）、`documents/reference/prompt-engineering/the-prompt-report.md`（§2.4 Prompt Engineering）、`documents/reference/prompt-engineering/prompt-pattern-catalog.md`（Question Refinement / Alternative Approaches）。

## 原則

改善は「言い換え」でなく「失敗の診断に基づく的を絞った編集」で行う。丸ごと書き直す前に、何が・なぜ効いていないかを特定する。

## 改善の手順

1. **失敗例を集めて検査**: 直したいプロンプトが実際に間違えた入出力を用意し、どこで・なぜ外したかを言語化（PE2 の hard negative sampling）。憶測で直さない。
2. **診断してから編集**: 「指示は正しくタスクを記述しているか」「欠落・誤解を招く箇所はどこか」を先に問う。原因を1つ以上の具体的な仮説に落とす。
3. **的を絞って編集**: 全文リライトでなく、診断した欠落・曖昧点をピンポイントで直す（例: 「必要に応じて足し算・引き算をすることを忘れずに」の一文追加）。言い換えだけの改変は効果が薄い。
4. **反復し、退行に備える**: 1回で決めず反復。プロンプトは些細な変化に敏感で、変更が改善どころか改悪になりうる。改善前後を比較し、悪化したら**元に戻せる**ようにしておく（バックトラック）。

## メタプロンプト（改善を指示するプロンプト）を書くときの3要素

改善作業自体を Claude に任せる／メタプロンプトを組むとき、PE2 が有効性を実証した3要素を入れる。

- **2段階のタスク記述**: 「Step 1: 現行プロンプトと失敗例を検査」「Step 2: 改善案を生成」と役割を分けて明示。
- **文脈指定**: プロンプトと入力データの結合方法（前後・区切り）を伝える。
- **段階的推論テンプレート**: 「タスクを正しく記述しているか？ 編集は必要か？ 必要なら実行可能な提案を出せ」と、検討の道筋を質問列で与える。

## 落とし穴

- **ショートカット学習**: 少数の例だけに合わせて最適化すると、意図と違う近道の規則を学び、その例では当たるが汎化しないプロンプトになる（PE2 のケーススタディ）。改善は保有する失敗例の外でも成り立つか疑う。
- **過剰な狭め込み**: 質問・スコープを洗練しすぎると大局的な観点を落とす（Question Refinement の帰結）。狭めた分、抜けた観点がないか確認。
- **モデル特化**: 特定モデル向けに詰めた最適化は他モデルへ汎化しないことがある。どのモデル前提かを意識。
- **単一情報源**: 改善で規約の具体値を指示文へ書き足すとドリフトする。値は `rules/` を唯一の正として参照（[[externalization-rule]]）。
