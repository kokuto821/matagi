# プロンプト改善（prompt improvement）のルール

既存プロンプト・スキル・サブエージェント指示文を**改善する**際の原則。ゼロから書く構成: [[composition-rule]]。本ルール =「既存物を直す」局面。

出典: `documents/reference/prompt-engineering/prompt-engineering-a-prompt-engineer.md`（PE2）、`documents/reference/prompt-engineering/the-prompt-report.md`（§2.4 Prompt Engineering）、`documents/reference/prompt-engineering/prompt-pattern-catalog.md`（Question Refinement / Alternative Approaches）。

## 原則

改善 =「言い換え」でなく「失敗診断に基づく的を絞り編集」。丸ごと書き直す前に、何が・なぜ効いていないか特定。

## 改善の手順

1. **失敗例を集めて検査**: 直したいプロンプトが実際に間違えた入出力を用意 → どこで・なぜ外したか言語化（PE2 の hard negative sampling）。憶測で直さない。
2. **診断してから編集**: 「指示は正しくタスクを記述しているか」「欠落・誤解を招く箇所はどこか」を先に問う。原因を1つ以上の具体的仮説に落とす。
3. **的を絞って編集**: 全文リライトでなく、診断した欠落・曖昧点をピンポイント修正（例: 「必要に応じて足し算・引き算をすることを忘れずに」の一文追加）。言い換えだけの改変は効果が薄い。
4. **反復・退行に備える**: 1回で決めず反復。プロンプトは些細な変化に敏感、変更が改善どころか改悪になりうる。改善前後を比較、悪化時**元に戻せる**ようにしておく（バックトラック）。

## メタプロンプト（改善を指示するプロンプト）を書くときの3要素

改善作業自体を Claude に任せる／メタプロンプトを組む際、PE2 が有効性を実証した3要素を入れる。

- **2段階タスク記述**: 「Step 1: 現行プロンプトと失敗例を検査」「Step 2: 改善案を生成」と役割を分けて明示。
- **文脈指定**: プロンプト・入力データの結合方法（前後・区切り）を伝える。
- **段階的推論テンプレート**: 「タスクを正しく記述しているか？ 編集は必要か？ 必要なら実行可能な提案を出せ」と、検討の道筋を質問列で与える。

## 落とし穴

- **ショートカット学習**: 少数の例だけに合わせ最適化 → 意図と違う近道規則を学習 → その例では当たるが汎化しないプロンプトになる（PE2 のケーススタディ）。改善は保有失敗例の外でも成り立つか疑う。
- **過剰な狭め込み**: 質問・スコープを洗練しすぎ → 大局的観点を落とす（Question Refinement の帰結）。狭めた分、抜けた観点がないか確認。
- **モデル特化**: 特定モデル向けに詰めた最適化 → 他モデルへ汎化しないことがある。どのモデル前提か意識。
- **単一情報源**: 改善で規約具体値を指示文へ書き足す → ドリフト。値は `rules/` を唯一の正として参照（[[externalization-rule]]）。
