# コンテキストは有限資源のルール

コンテキスト（推論時に載るトークンの集合）は、無限に足せる入力でなく **限界収穫逓減する有限資源** として扱う。スキル・エージェント・AGENTS.md/CLAUDE.md・単発プロンプトのどれを設計する場合も、この前提から出発。

出典: `documents/reference/context-engineering/effective-context-engineering-for-ai-agents.md`（以下 blog、「なぜ重要か」「効果的なコンテキストの解剖学」）、`documents/reference/context-engineering/a-survey-of-context-engineering-for-large-language-models.md`（以下 survey、§3.2.1 / §4.3.1）。

## 原則：高シグナルなトークンの最小集合を狙う

**望ましい結果の実現可能性を最大化する、高シグナルなトークンの最小集合を探す。**

- **「最小」＝「短い」ではない。** 望ましい挙動を確実に守らせるのに必要な情報は前もって十分に与える。削って挙動が崩れるなら最小集合ではない。
- **まず最小で測り、失敗モードを見て足す。** 利用可能な最良のモデルで最小限のプロンプトを試し、実際の失敗を確認してから、明確な指示や例を **狙って** 追加。想像上のエッジケースを先回りで詰め込まない。
- **惰性で足さない。** 要素を1つ足すたび「このタスクに本当に効くか」を問う。必要情報だけに絞れば、少ないトークンで同等の品質を出せる（survey §3.2.3）。

## 背景：注意予算と context rot

「多いほど良い」が成り立たない理由。

- **注意予算（attention budget）**：LLM は大量のコンテキスト解釈に有限の「注意」を消費。新しいトークンを入れるたび予算は減る。
- **context rot**：コンテキスト内トークンが増えるほど、情報を正確に想起する能力は低下。程度差こそあれ全モデルに現れる。
- **構造的な理由**：Transformer は n トークンで n² 通りのペア関係を持ち、長くなるほど注意が薄く引き伸ばされる。加えて訓練分布は短い系列が多く、長距離依存の経験・専用パラメータが少ない。位置エンコーディングの補間も長系列では劣化を伴う。断崖でなく **性能の勾配（グラデーション）** が生じる。
- **中盤の脱落（lost-in-the-middle）**：長い入力の中盤に置いた情報は抜け落ちやすい（survey §4.3.1）。重要な指示・データを長文の中央に埋めない。

「詰め込めば賢くなる」という直感の否定。ゆえに載せるトークンを慎重にキュレーションする価値がある。

## 適用の指針

- プロンプト／ルール／AGENTS.md/CLAUDE.md が長くなったら、まず「削れるトークン」を疑う。冗長な前置き・重複説明・使われない例を削る。
- 常時ロードされるもの（AGENTS.md/CLAUDE.md・未スコープ rule）ほど予算への影響が大きい。手順は skill へ、限定的な文脈は path スコープや `[[link]]` 参照へ寄せる（→ `[[selection-rule]]`）。
- 「最小十分」の判断がつかないとき、削った版と足した版を実際に走らせて挙動差を見る。
