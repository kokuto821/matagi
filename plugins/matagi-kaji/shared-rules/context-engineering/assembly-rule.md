# コンテキストの構成・組み立てルール

コンテキストは「一枚の固定した文字列」でなく、**複数の情報部品を整形して並べたもの**として設計する。何を・どの高度で・どんな区切りで・どの順に載せるかが出力品質を決める。

対象は「文脈の組み立て方」。プロンプト本文そのものの構成要素の過不足は [[composition-rule]]、区切りへの敏感さ・頑健性は [[robustness-rule]] を参照（本ルールと役割分担）。

出典: `documents/reference/context-engineering/effective-context-engineering-for-ai-agents.md`（以下 blog、「効果的なコンテキストの解剖学」）、`documents/reference/context-engineering/a-survey-of-context-engineering-for-large-language-models.md`（以下 survey、§3.1）。

## 1. 適切な「高度（altitude）」を狙う

システムプロンプト・指示は、2つの失敗モードの中間（Goldilocks ゾーン）に置く。

| 極端 | 症状 | 問題 |
|------|------|------|
| 低すぎる高度 | 挙動を脆い if-else でハードコードする | 脆弱・保守コスト増。想定外入力で崩れる |
| 高すぎる高度 | 曖昧で一般的すぎる指示。共有文脈を勝手に前提化 | 具体的シグナルが無く挙動が定まらない |
| **ちょうどよい** | 挙動を導けるほど具体的、かつ強力なヒューリスティクスを与えられるほど柔軟 | モデルの判断力を活かしつつ方向づけできる |

- 正確な挙動を1つ残らず条件分岐で書き切ろうとしない。**強いヒューリスティクスを与えて判断を委ねる**方向へ寄せる。
- 逆に「良い感じにやって」で済ませない。何を良しとするかの具体的シグナルは与える。

## 2. セクションで区切る

プロンプトは明確に区別したセクションに整理し、XML タグや Markdown 見出しで区切る。

- 例：`<background_information>` / `<instructions>` / `## Tool guidance` / `## Output description`。
- 背景・指示・出力仕様を混線させない。
- **注記**：モデルが高能力になるほど、フォーマット厳密さの重要度は逓減。区切りは「モデルが迷わないための補助」であり、目的ではない。凝った書式に労力を割きすぎない。

## 3. 部品として組み立てる（Format → Concat）

コンテキストは次の部品を整形（Format）し連結（Concat）した結果と捉える（survey §3.1）。

| 部品 | 中身 |
|------|------|
| c_instr | システム指示・ルール |
| c_know | 外部知識（RAG で取得する知識など） |
| c_tools | 使えるツールの定義 |
| c_mem | 過去のやり取りから引き継ぐ記憶 |
| c_state | ユーザー・世界・エージェント系の現在の状態 |
| c_query | ユーザーの今の要求 |

- 品質を決めるのは個々の文言だけでない。**部品の選び方・並べ方・整形の仕方**も決める。組み立て方そのものを設計対象とする。
- 各部品は「このタスクに要るか」で取捨。不要な部品を惰性で載せない（→ [[budget-rule]]）。
- 可変の入力データを差し込むとき、指示とデータの境界を区切りで明示（→ [[robustness-rule]]）。
