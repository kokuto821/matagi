# 決定論的処理のスクリプト化ルール

## 原則

**入力→出力が一意に定まり、モデル判断を要さない処理 = モデルに解釈させずスクリプトに判定させる。** スクリプト化 = 判定をスクリプトが取り切り、モデルは結果を受け取るのみ。

## 判断基準

### スクリプト化の候補になる条件（全て満たす）

| 条件 | 内容 |
|------|------|
| 一意性 | 同じ入力→必ず同じ出力 |
| 判断不要 | 意味解釈・文脈依存・良し悪しの判断を含まない |
| 機械記述可 | 判定規則を機械的に書き下せる（存在確認・形式検証・パース・集計・件数上限・差分取得・名前規則照合など） |

### 見送る条件（1つでも該当。候補条件より優先）

| 条件 | 理由 |
|------|------|
| 意味解釈・要約・方針判断を含む | 判断をスクリプトで偽装できない |
| 実行頻度が低い・一回きり | 保守コスト > 便益 |
| 既存の linter・hook・テストで判定済み | 二重管理 |
| 実行環境をプロダクトが保証しない | 動かない保証は強制にならない |

判定できない（頻度・環境が不明など）場合は、Suggestion に格下げし、判定できなかった理由を添える。

### 効果が大きい候補

- 頻繁に実行される
- モデルの誤判定・ぶれが成果に響く
- 判定のためにモデルが全量を読み、コンテキストを消費する

## 言語選択

優先順位 = **mts > python > sh**（mts = TypeScript 系。`.mts` / `.ts`）。

- 上位言語で書けるかを先に判断。書けない理由が明確なときのみ次点へ下げる
- 置き場所・実行方式 = 本ルール対象外（スクリプト化を実施する issue で決める）

## 適用手順

1. 対象資産の指示文から、モデルが機械的にこなしている処理を列挙
2. 判断基準で候補・見送りに振り分け
3. 候補 = 該当箇所・スクリプト化できる理由・推奨言語を指摘（適用は別の産出者・別 issue。[[review-independence-rule]]）

## やってはいけないこと

- 意味判断を要する処理のスクリプト化（機械判定の偽装）
- スクリプトを用意しつつ、実行・遵守をモデルの自己判断に任せる（助言強度のコード。[[harness-rule]] §中間の折衷を避ける）
- スクリプト化後も元のプロンプト記述を残す（二重管理）。削除または呼び出し指示へ差し替える
- スキル・エージェント側へ本ルールの基準を再掲（[[externalization-rule]]）

## 背景

機械判定できる処理が Markdown 指示としてモデルに委ねられ、解釈のぶれとコンテキスト消費を招く。

[[harness-rule]] との違い = 判定軸。harness-rule = 「破られたら困るか」で保証の要否を判定。本ルール = 「モデル判断を要するか」で解釈ぶれ・コンテキスト消費の排除要否を判定。
