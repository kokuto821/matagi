# レビュー独立性ルール

## 原則

**レビュワーは、レビュー対象を産出したエージェントであってはならない。** 実装コード・書いたテスト・当てた修正を本人（同一エージェント）に評価させない。**1エージェント＝1役割**：「評価（レビュー・指摘）」「産出（実装・修正適用）」を1エージェントに同居させない。

例外（「レビュー→修正なら順序が守るから同一でも可」等）は設けない。単純さ優先。

## なぜか

自作物の自己レビュー → 2つの理由で評価劣化。

1. **甘さ（leniency）**: 自分の成果物 → 評価が甘くなる。厳しめプロンプトで ある程度は打ち消せる。
2. **共有された盲点（shared blind spots）**: 実装時に仕様を読み違えたエージェント → レビュー時も同じ読み違いを保持。その誤解由来バグを **原理的に** 見つけられない。同じモデルが同じ推論をする以上、プロンプトでは消せない。

重要：**クリーンな文脈（別invocation）は 2 の代替にならない**。盲点の由来 = 文脈汚染でなく推論傾向 → 「実装と別呼び出しでレビューさせるから安全」は不成立。ゆえに *別エージェント* 必須。

## 帰結

- 各ドメイン **レビュー専用エージェント（`*-reviewer`）**・**産出者（実装／修正適用専用）** を分ける。前者は指摘のみ、後者は承認済み指摘の適用のみ担う。
- **修正適用後の再検証も、修正した本人にはさせない**。別レビュワー、またはレビュースキル再実行で確認。
- 産出者を「レビューもできる」設計にしない（`*-engineer` / `ui-designer` / `frontend-*` の2モード化を避ける）。役割は front-matter・本文どちらでも単一に保つ。

## 適用外（単一エージェントで良いケース）

レビュー対象が **他者（メインエージェント／ユーザー）の成果物**、かつ当該エージェント自身が産出を伴わない純レビュー → 単一エージェントで良い。レビュワーの通常形。本ルールが禁じる「自作物の自己レビュー」には当たらない。
