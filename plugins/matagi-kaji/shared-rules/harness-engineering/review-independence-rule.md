# レビュー独立性ルール

## 原則

**レビュワーは、レビュー対象を産出したエージェントであってはならない。** 実装コード・書いたテスト・当てた修正を本人（同一エージェント）に評価させない。**1エージェント＝1役割**：「評価（レビュー・指摘）」「産出（実装・修正適用）」を1エージェントに同居させない。

例外（「レビュー→修正なら順序が守るから同一でも可」等）は設けない。単純さ優先。

## なぜか

自作物の自己レビュー → 2つの理由で評価劣化。

1. **甘さ（leniency）**: 自分の成果物 → 評価が甘くなる。厳しめプロンプトで ある程度は打ち消せる。
2. **共有された盲点（shared blind spots）**: 実装時に仕様を読み違えたエージェント → レビュー時も同じ読み違いを保持。その誤解由来バグを **原理的に** 見つけられない。同じモデルが同じ推論をする以上、プロンプトでは消せない。

重要：**クリーンな文脈（別invocation）は 2 の代替にならない**。盲点の由来 = 文脈汚染でなく推論傾向 → 「実装と別呼び出しでレビューさせるから安全」は不成立。ゆえに *別エージェント* 必須。

## 帰結

- 各ドメイン **レビュー専用エージェント（`*-reviewer`）**・**産出者（実装／修正適用専用）** を分ける。前者は指摘のみ、後者は承認済み指摘（承認主体 = ユーザー。§指摘適用の承認）の適用のみ担う。
- **修正適用後の再検証も、修正した本人にはさせない**。別レビュワー、またはレビュースキル再実行で確認。
- 産出者を「レビューもできる」設計にしない（`*-engineer` / `ui-designer` / `frontend-*` の2モード化を避ける）。役割は front-matter・本文どちらでも単一に保つ。

## 指摘適用の承認

**レビュー指摘を産出者へ戻して適用させる前に、ユーザーの承認を得る。** 指摘が妥当でも、ユーザーの意図（スコープ・既存方針）と食い違う修正を含みうるため。レビュー→適用を統括するスキル（オーケストレーター）が担う。

| 状況 | どうする |
|------|---------|
| レビューが指摘を返した | 重大度順（[[severity-rule]]（`matagi/shared-rules/review-severity/severity-rule.md`））に提示→適用する指摘をユーザーに確認→**承認された指摘のみ**産出者へ委譲 |
| 複数ラウンドの再レビューで指摘が返った | **毎ラウンド**同様に確認。初回承認を以降ラウンドへ流用しない |
| 承認されなかった指摘 | 適用しない。以降ラウンドで再確認せず、**残課題として最終報告に残す**。同一指摘の判定 = 同一箇所かつ同一根拠ルール。迷う場合は新規扱いで確認 |
| 各ラウンドの承認・適用を終えた | 承認結果（承認／不承認の指摘要旨）を git 管理外のノートに退避。次ラウンド冒頭でノートを読み戻し、不承認済みとの照合に使う（[[long-horizon-rule]]（`shared-rules/context-engineering/long-horizon-rule.md`））。会話記憶だけに頼らない |
| 承認された指摘が1件もない | 適用せず次工程へ進む（不承認分は上段どおり残課題） |
| ユーザーが「確認なしで進めて」「全自動でやって」等を明示 | 確認省略可。適用対象 = 不承認済みを除く全件（[[issue-driven-rule]]（`matagi/shared-rules/issue-driven-development/issue-driven-rule.md`）§副作用を伴う git / GitHub 操作 の明示指示と同じ扱い）。エージェントから省略を持ちかけない |
| 起動したレビュースキル自身が承認ゲートと適用委譲を持つ（ui-review / prompt-review / context-engineering-review 等） | そのスキル内の承認・適用で完結。呼出側で同じ指摘を再確認せず、産出者へ再委譲もしない（二重承認・二重適用回避） |

## 適用外（単一エージェントで良いケース）

レビュー対象が **他者（メインエージェント／ユーザー）の成果物**、かつ当該エージェント自身が産出を伴わない純レビュー → 単一エージェントで良い。レビュワーの通常形。本ルールが禁じる「自作物の自己レビュー」には当たらない。
