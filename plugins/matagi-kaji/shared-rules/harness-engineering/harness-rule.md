# ハーネス制御の媒体選択ルール

## 原則

**コードで書けるものはコードで書く。Markdown には書けないものだけを `.md` に書く。**

| 媒体 | 向いているもの | 向いていないもの |
|------|--------------|----------------|
| `.sh` / `.ts` / `.js` | 保証・強制・決定論的制御 | モデルへのソフト指針 |
| `.md` (AGENTS.md / CLAUDE.md, rules/) | コンテキスト・方針・規約 | セキュリティ・安全ガード |

## 判断基準：「破られたら困るか」

| 判定 | 例 | 置き場所 |
|------|----|----------|
| 破られたら困る（安全・課金・データ破壊系） | `rm -rf` ブロック、パーミッション制限、リトライ上限 | コード（`.sh` / `.ts` / `.js`） |
| 破られても許容可（スタイル・文脈系） | コーディング規約、出力トーン、ライブラリ好み | Markdown（`.md`） |

## なぜコードに置くのか

Markdown = モデルが「読んで解釈する"お願い"」にすぎない。実行セマンティクスなし。
prompt injection で賢いモデルほど説得・回避しうる。

コード = モデルの振る舞い問わず迂回不能。セキュリティ・制御の核心部分では
「より良い」でなく**保証を与えられる唯一の手段**。

## 具体的な使い分け

### コード（`.sh` / `.ts` / `.js`）に書くもの

- パーミッション判定・deny リスト（未許可ツール呼び出しのブロック）
- フック処理（pre-commit, post-tool など）実行ロジック
- リトライ・トークン管理・状態マシンのループ
- 環境変数検証、シークレット存在チェック
- 自動化スクリプト（定型操作のシェルスクリプト化）

### Markdown（`.md`）に書くもの

- プロジェクト方針・背景・目標
- コーディング規約・ライブラリ選好
- 出力フォーマット・トーン指針
- 「なぜ」説明（コメントより AGENTS.md / CLAUDE.md が適切な場合）
- モデル判断を「導く」文脈

## 適用手順

1. 追加する指示・制御を確認
2. 「破られたら困るか」で判定
3. 困る → コードファイル実装（hooks、スクリプト、settings.json）
4. 困らない → `.md` に記述
5. 両要素混在 → 分割して書く

## 中間の折衷を避ける（コードを選ぶなら保証まで取り切る）

「コードで書く」と決めたら迂回不能な**保証**まで取り切る（hook・deny リスト・settings.json）。
コード（スクリプト＋状態ファイル）を用意しつつ遵守をモデルの自己判断に委ねる
**「助言強度のコード」= 最悪の折衷**。コードのコスト（可搬性・exit code 解釈・状態管理・
レビュー対象増加）を負いながらコード化便益（強制）を得られないため。

判断は二択に振り切る:

- **本当に破られたら困る** → コードで強制（例: commit を捕捉する hook）。散文の"お願い"に頼らない。
- **破られても許容できる** → Markdown 散文に留める。決定論のためだけにスクリプトを足さない。

### 対話型か自律型かで強制の要否は変わる

同じ「上限」でも実行文脈で判定変化。**メインスレッドで進行が可視・中断可能な対話型スキル**は
暴走をユーザーが観測・停止可能 → hook 強制は多くの場合過剰。一方**バックグラウンド／自律
エージェントの無人ループ**は観測者不在 → リトライ上限などコード強制の価値が高い。
「破られたら困るか」は**誰が見ているか**（実行文脈）込みで判定。
