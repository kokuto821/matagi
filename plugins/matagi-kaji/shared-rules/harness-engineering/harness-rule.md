# ハーネス制御の媒体選択ルール

## 原則

**コードで書けるものはコードで書く。Markdown には書けないものだけを `.md` に書く。**

| 媒体 | 向いているもの | 向いていないもの |
|------|--------------|----------------|
| `.sh` / `.ts` / `.js` | 保証・強制・決定論的制御 | モデルへのソフトな指針 |
| `.md` (AGENTS.md / CLAUDE.md, rules/) | コンテキスト・方針・規約 | セキュリティや安全ガード |

## 判断基準：「破られたら困るか」

| 判定 | 例 | 置き場所 |
|------|----|----------|
| 破られたら困る（安全・課金・データ破壊系） | `rm -rf` ブロック、パーミッション制限、リトライ上限 | コード（`.sh` / `.ts` / `.js`） |
| 破られても許容できる（スタイル・文脈系） | コーディング規約、出力のトーン、ライブラリの好み | Markdown（`.md`） |

## なぜコードに置くのか

Markdown はモデルが「読んで解釈する"お願い"」にすぎない。実行セマンティクスなし。
prompt injection で賢いモデルほど説得・回避しうる。

コードは、モデルがどう振る舞おうと迂回不能。セキュリティ・制御の核心部分では
「より良い」でなく、**保証を与えられる唯一の手段**。

## 具体的な使い分け

### コード（`.sh` / `.ts` / `.js`）に書くもの

- パーミッション判定・deny リスト（許可していないツール呼び出しのブロック）
- フック処理（pre-commit, post-tool など）の実行ロジック
- リトライ・トークン管理・状態マシンのループ
- 環境変数の検証、シークレットの存在チェック
- 自動化スクリプト（定型操作のシェルスクリプト化）

### Markdown（`.md`）に書くもの

- プロジェクトの方針・背景・目標
- コーディング規約・ライブラリの選好
- 出力フォーマット・トーンの指針
- 「なぜ」の説明（コメントより AGENTS.md / CLAUDE.md が適切な場合）
- モデルの判断を「導く」ための文脈

## 適用手順

1. 追加する指示・制御を確認
2. 「破られたら困るか」で判定
3. 困る → コードファイルで実装（hooks、スクリプト、settings.json）
4. 困らない → `.md` に記述
5. 両方の要素が混在 → 分割して書く

## 中間の折衷を避ける（コードを選ぶなら保証まで取り切る）

「コードで書く」と決めたら、迂回不能な**保証**まで取り切る（hook・deny リスト・settings.json）。
コード（スクリプト＋状態ファイル）を用意しつつ、遵守をモデルの自己判断に委ねる
**「助言強度のコード」は最悪の折衷**。コードのコスト（可搬性・exit code の解釈・状態管理・
レビュー対象の増加）を負いながら、コード化の便益（強制）を得られないため。

判断は二択に振り切る:

- **本当に破られたら困る** → コードで強制（例: commit を捕捉する hook）。散文の"お願い"に頼らない。
- **破られても許容できる** → Markdown の散文に留める。決定論のためだけにスクリプトを足さない。

### 対話型か自律型かで強制の要否は変わる

同じ「上限」でも実行文脈で判定が変わる。**メインスレッドで進行が可視・中断可能な対話型スキル**は、
暴走をユーザーが観測して止められるため、hook 強制は多くの場合過剰。一方、**バックグラウンド／自律
エージェントの無人ループ**は観測者がいないため、リトライ上限などはコードで強制する価値が高い。
「破られたら困るか」は**誰が見ているか**（実行文脈）込みで判定。
