# スキル・エージェント テンプレートルール

## テンプレートの置き場所

| 種類 | テンプレートパス |
|------|----------------|
| スキル | `plugins/matagi-kaji/template/skills/SKILL.md` |
| サブエージェント | `plugins/matagi-kaji/template/agents/AGENT.md` |

## スキルテンプレート

### フロントマター

最小構成は `name` と `description` のみ。他は必要なときだけ追加する。

```yaml
---
name: skill-name        # ディレクトリ名と一致させる（kebab-case）
description: >          # 最重要。自動起動トリガー。要点を先頭に書く
  ...
---
```

オプションフィールド:

| フィールド | 追加するとき |
|-----------|-------------|
| `when_to_use` | description を補完するトリガー条件がある場合 |
| `allowed-tools` | 使用ツールを明示的に制限したい場合 |
| `disable-model-invocation: true` | 副作用があるタスク型で手動起動のみにしたい場合 |
| `context: fork` | 別コンテキストで隔離実行したい場合 |

### 本文

> **スキル本文構成の定義はここを唯一の出典とする。** テンプレート本体（`template/skills/SKILL.md`）はこれを体現し、`create-skill` はこれを参照する。各所で構成を文章で再記述しない。

- **500行未満**を目安に保つ（ロード後セッション中ずっとコンテキストに残るため）
- 詳細なリファレンスは別ファイルに分離する
- 構成: 「概要」→「ルール」→「手順」→「出力」が基本

| ブロック | 内容 | 省略 |
|---------|------|------|
| 概要 | 何をするスキルか（1〜2行） | 不可 |
| ルール | このスキルが従う規約・判断基準。本文に直書きせず `rules/` / `reference/` を参照する（[[externalization-rule]]） | ルールが無いスキルは省略可 |
| 手順 | 実行ステップ。mermaid `flowchart TD` で書く（§手順の記述形式） | 手順を持たない参照型は省略可（§適用除外） |
| 出力 | ユーザーに返す形式 | 不可 |

### タスク型 vs 参照型

| 種類 | 判断基準 | ポイント |
|------|---------|---------|
| タスク型 | デプロイ・コミットなど副作用あり | `disable-model-invocation: true` で手動起動に |
| 参照型 | 規約・スタイルガイドなど知識提供 | インラインで知識として効かせる |

## サブエージェントテンプレート

### フロントマター

最小構成は `name` と `description` のみ。

```yaml
---
name: agent-name
description: 委譲条件を具体的に書く
---
```

オプションフィールド:

| フィールド | 追加するとき |
|-----------|-------------|
| `tools` | ツールを制限したい場合（**省略すると全ツールを継承**） |
| `model` | コスト最適化したい場合（探索系は `haiku`）。省略で `inherit` |
| `memory` | 会話をまたいで学習を蓄積させたい場合 |

`tools` は**省略するとメイン会話の全ツールを継承**する。読み取り専用のレビュー役など安全性を担保したいエージェントには必ず指定する。

### 本文（システムプロンプト）

本文がそのままシステムプロンプトになるため、構造化することで指示追従性が上がる。

推奨構成:

```
あなたは〇〇の専門家です。   ← 役割（1行）

呼ばれたときの手順:          ← 何をするか（mermaid flowchart TD ＋ 各ステップの詳細）
1. ...

チェックリスト / 観点:       ← 何を見るか
- ...

出力フォーマット:             ← どう返すか
- ...
```

見出し（`##`）と「ラベル + コロン」はどちらでも効果は同等。本文が長くなったら `##` に切り替える。手順の書き方は §手順の記述形式 に従う。

## 手順の記述形式（スキル・サブエージェント共通）

> **手順の記述形式の定義はここを唯一の出典とする。** テンプレート本体（`template/skills/SKILL.md`・`template/agents/AGENT.md`）はこれを体現する。各所で記法を文章で再記述しない。

**手順（実行ステップ・分岐・ループ・停止条件を含む記述）は mermaid `flowchart TD` で書く。** 番号リストや散文だけで分岐を表さない。条件分岐が文章に埋もれて解釈がぶれるのを防ぎ、フローの可読性を上げるため。下の「書き方」の表の記法、色分けの固定定義、図の直下の固定文は、該当するものをすべて必須とする。

### 書き方

| 要素 | 記法 |
|------|------|
| 方向 | `flowchart TD` 固定。`LR`・`sequenceDiagram`・`stateDiagram` は使わない |
| 置き場所 | 手順に当たるセクション（見出し名は問わない。`## 手順`・`# 指示`・「呼ばれたときの手順」など）の直下に mermaid ブロックを1つ置く。その下に固定文（後述）、続けて各ステップの詳細を書く |
| レーン | **各手順を1つの `subgraph`（スイムレーン）で囲む。** 区切りは、`### N.` の見出しがあれば見出し単位、無ければ番号項目単位とし、散文の番号は付け替えない。ID は `L<連番>`、タイトルは `"<番号> <見出し>"`（見出し・項目の要旨から作り、「—」などの装飾記号は除く）。すべての処理・判定ノードはいずれかのレーンに属する |
| 宣言位置 | ノードは自レーンの `subgraph` 内で宣言し、レーン内のエッジもそこに書く。レーンをまたぐエッジは、すべての `subgraph` の後にまとめて書く（mermaid ではノードの所属が宣言位置で決まるため）。`classDef` と `class` 文はブロックの末尾にまとめ、インデントは4スペースとする |
| 開始・終了 | `START(["START"])` / `END(["END"])` に統一する（ID・ラベルとも大文字。mermaid では小文字の `end` が予約語のため）。待機・他フェーズへの移動など、流れをそこで止めるノードは終端形 `([...])` で書き、内容をラベルにする（ID は内容を表す英語名でよい。例: `Resume`・`Wait`）。終端ノードはレーンに入れず、先頭で宣言する |
| 処理 | `S1a["入力を集める"]`。ID は `S<手順番号><連番文字>`（`S1a`・`S1b`…。連番文字は散文の副番号 8a・8b などとは無関係）。ラベルは何をするかを短い動詞句で書く |
| 分岐 | `S1b{"issue 化すべきか？"}`。判定ノードは「〜か？」の疑問形で書き、出るエッジは `-->|YES|` と `-->|NO|` の2本にする |
| 3択以上の分岐 | YES / NO の判定を連鎖させる。連鎖の順が評価順になる。「上から順に評価し、最初に該当したものを使う」表はそのまま連鎖になる |
| ループ・差し戻し | 戻りエッジで表す。回数上限などの停止条件は「上限に達したか？」の判定ノードにし、YES を報告ノード（または終端ノード）へ出し、報告後は END か後続の手順へ進める。ユーザーの応答を待つ再提示のループには上限を置かない |
| 承認ゲート | 「承認されたか？」の判定ノードにし、NO は修正して再提示する前のノードへ戻す |
| 実行主体の色分け | `classDef user`（黄）: ユーザーに確認・承認・選択・判断を求めるノード（凡例では「確認・承認」と書く）。質問ノード、ユーザーの回答で分岐する判定ノード、承認ゲートが対象で、提示だけのノードには付けない。`classDef delegate`（青）: 他スキル・エージェントの起動を伴うノード。産出者への差し戻し適用とレビューの再実行を含む。両方に当たるノードは黄を優先する。該当ノードがある色は必ず付け、該当ノードが無い色は定義しない |
| ラベルの文字 | ラベルは `"..."` で囲む。バッククォート・`<` `>`・`#`・`;` は使わない。読点・括弧は半角スペースに置き換える。回数上限などの数値、ファイルパス、フラグ・引数付きのコマンドは書かない（散文に書く。コマンド名と委譲先名は、何をするかを示すために書いてよい） |
| 常時制約 | 手順ではない常時の制約・禁止（「〜しない」「格上げしない」など）は図に載せず、散文に残す。制約と条件付きのステップが混在する項目は、ステップだけを図に載せ、見出しは中立語（「結果を返す」など）にする。制約のみの項目はレーンを作らない |

色分けの固定定義（ライト・ダークどちらでも読めるよう文字色を明示している）:

```
classDef user fill:#fff3bf,stroke:#f08c00,color:#000
classDef delegate fill:#d0ebff,stroke:#1971c2,color:#000
```

図の直下に、次の固定文を1行置く: `遷移は図に従い、判定基準・詳細は下の本文に従う。`

色分けを付けた場合は、その下に凡例の固定文を1行置く: `凡例: 黄 = ユーザーの確認・承認、青 = 他スキル・エージェントへの委譲`。使った色の項目だけを書く（黄だけなら `凡例: 黄 = ユーザーの確認・承認`、青だけなら `凡例: 青 = 他スキル・エージェントへの委譲`）。

テンプレートに置いた手順の記述形式へのポインタ（HTML コメント）は、スキル・サブエージェントの生成後に削除してよい。

### 役割分担（二重管理を避ける）

- フローチャートは**遷移**（どこへ進む・戻る・止まるか）の正とする。
- 散文は各ノードの**詳細**（何をもって YES とするかの判定基準・数値・コマンド・委譲先・出力）を書く。散文側に遷移を再掲しない。
- 判定ノードのラベルは短い疑問形にとどめ、判定基準は散文に書く。
- 食い違いが見つかった場合は図を正とする。既存の資産には、段階導入のため散文に遷移の記述が残っている。散文から遷移の記述を整理する作業は別 issue で扱い、本ルールは新規作成・更新時の書き方を定める。

### 適用除外

手順に当たるセクション自体が無いスキル／サブエージェント（スタンスの列挙・出力形式の定義のみのもの）は、フローチャートを置かない。手順に当たるセクションがあるものは、直線的な手順にも一律に置く。図の要否を作者の裁量にせず、検査とレビューを単純にするため。

## スキルとエージェントの連携

- エージェント側に `skills:` フィールドを書くと、起動時にそのスキルの全文がコンテキストに注入される
- スキル側に `context: fork` と `agent:` を書くと、タスクとして指定エージェントで隔離実行できる
